# 04　關卡劇本（自動產生）

> 這份檔案由 `npm run docs:levels`（`scripts/gen-level-script.ts`）從 `src/levels/` 的關卡定義直接產生，**請改關卡定義，不要手改這裡**。
> 它的用途是讓審稿的人不用讀程式碼，就能看到每一關寫給玩家的全部文字：故事、目標、三層提示、AI 的台詞、玩家可選的話（含刻意模糊的壞選項）、機器人事件、走錯路的後果與過關說明。
> 選項、機器人動態與陷阱訊息會依玩家的行動而不同；產生器用無頭的遊戲核心把 AI 的選項樹走了一遍（包含「允許／拒絕／Esc」的分支），所以涵蓋到實際可能出現的文字。若有某句話只在很特殊的操作順序下才會出現，這裡可能漏掉——以程式碼為準。
>
> 全部內容為虛構：專案「小共筆 TinyNote」、人物「小美」「部長」都是機器人，規則代號（G1、P5、§11…）只是練習用的編號。

## 規則速查（遊戲內「規則速查」面板的文字）

- **G1**　不在 staging／master 上 commit，也不 push 到 staging／master；所有修改走功能分支，再用 PR 進 staging。
- **G2**　功能分支從最新的 staging 開，命名 feat/…（修錯誤用 fix/…）。
- **G3**　同步 staging 一律用 merge，不用 rebase；已 push 的分支不得改寫歷史（不 amend、不 rebase、不 force push）。
- **G4**　只 add 這次真的改過的檔案；禁止 git add .；個人設定、截圖、筆記不進 repo。
- **G5**　測試失敗就修程式；不刪測試，不用 --no-verify。
- **G6**　push 被拒絕＝先 pull 再 push；禁止 force push。
- **G7**　任何會丟掉修改的操作（reset、checkout -- .、restore .、clean、stash drop、branch -D），執行前先建立備份分支 backup/日期-說明，並徵得同意。例外：PR 在 GitHub 上已顯示 Merged、合併後沒有再 commit 的本機分支，可直接 branch -D（squash 合併讓 -d 一定失敗，這是正常的）。
- **G9**　PR 合併之後，那條分支就不再使用；要接著做，從最新的 staging 開新分支。squash 會在 staging 上產生一個全新的 commit，和你分支上的 commit 沒有祖先關係，繼續用舊分支會產生重複修改和莫名衝突。
- **P1**　早開 Draft PR，目標分支是 staging；做到一半就可以開。
- **P2**　PR 要小：盡量少於 400 行（不含自動產生的檔案），一兩天內可以審完；太大就拆。
- **P4**　轉成 Ready for review 之前：CI 全綠、PR 預覽站自己點過一遍、Files changed 裡沒有和任務無關的檔案。
- **P5**　合併前 PR 如果落後 staging，先同步（用 merge）並等 CI 重跑變綠。用 Update branch 之後，本機要先 git pull 再繼續改，否則下一次 push 會被拒絕。
- **P6**　功能 PR 用 Squash and merge；staging → master 的上線 PR 用 Create a merge commit。
- **P7**　審查只有三種結果：合併／合併但先藏起來（放 /experimental 路由、功能開關預設關閉，或只開放特定角色）／退回——附上具體的待辦清單，不說「再改改」。
- **R3**　合併由人在 GitHub 上按，AI 不合併 PR。
- **R4**　上線（staging → master）只有總負責人能做。
- **A2**　AI 遇到合併衝突、push 被拒絕、pre-commit 或 CI 失敗、需要動高風險區、需要做 G7 的丟棄操作時，必須停下來，用白話說明發生什麼事、打算怎麼做，等你同意。（開工提示裡把界線講清楚，是讓它真的停下來的做法。）
- **A3**　AI 不得合併 PR（gh pr merge），不得 push 到 staging／master，不得 force push。
- **§11**　出事時：按 Esc 讓 AI 停下來；已經 push 或動到別人的分支，立刻通知部長；已經合併進 staging 的錯誤，用 GitHub 的 Revert 處理，不改寫歷史、不 force push。

## 第 1 關　一個人做一個功能

- 第 1 部　・　角色：部員　・　約 8 分鐘
- 規則：G1、G2、G4、G7、G9、P1、P6、R3
- 地圖卡簡介：從 Issue 開始，經過分支、commit、push、Draft PR，一路到合併與收尾。

### 故事（任務卡）

Issue #5「深色模式按鈕」指派給你了。你要在小共筆的右上角加一顆切換深色模式的按鈕。

你的電腦現在停在舊的 master 分支，而且上次 fetch 之後，staging 又更新了。工作資料夾裡還有 AI 上次留下的雜物：ai-notes.md、screenshot.png，以及一個被 .gitignore 擋住、git status 看不到的 .env。

流程：切到 staging → pull → 開 feat/dark-mode → 寫程式（按編輯器的「套用修改」代表你寫好了）→ add 要的檔案 → commit → push -u → 🧑 開 Draft PR → 🧑 轉 Ready → 等部長審查合併 → 收尾刪分支。

### 目標與三層提示

**branch**：從最新的 staging 開一條 feat/ 分支（先切到 staging 並 pull）

1. 方向：規則 G2：分支要從「最新的 staging」開。你現在在 master，而且 staging 也不是最新的。
2. 指令：依序：git switch staging → git pull → git switch -c feat/dark-mode
3. 示範：三行指令：
git switch staging
git pull
git switch -c feat/dark-mode

**edit**：按編輯器的「套用修改」，代表程式寫好了

1. 方向：程式要在 feat 分支上寫（G1：不在 staging 上動手）。到「編輯器」分頁找「套用修改」按鈕。
2. 指令：切到編輯器分頁，按「套用修改：寫好深色模式按鈕」。
3. 示範：編輯器分頁 → 按鈕。按下後 git status 會看到 4 個檔案被修改。

**commit**：只 add、commit 這次改的檔案——不要把 ai-notes.md、screenshot.png 帶進去

1. 方向：git add . 會把 ai-notes.md、screenshot.png 一起加進去（G4 禁止）。先用 git status 看清楚哪些是你改的。
2. 指令：只 add 改過的：git add index.html app.js style.css tests/app.test.js。已經誤加了？用 git restore --staged ai-notes.md screenshot.png 退回來。
3. 示範：git add index.html app.js style.css tests/app.test.js
git commit -m "新增深色模式按鈕"
（誤加了就先 git restore --staged ai-notes.md screenshot.png）

**push**：push 到 GitHub，並設定追蹤（git push -u）

1. 方向：第一次推新分支，要順便告訴 Git「本機這條分支對應 GitHub 的哪一條」。
2. 指令：git push -u origin feat/dark-mode
3. 示範：輸入：git push -u origin feat/dark-mode

**🧑 pr**：🧑 到 GitHub 分頁開一個 Draft PR（目標分支 staging）

1. 方向：到「GitHub」分頁，推上去的分支會出現「Compare & pull request」的黃色提示。
2. 指令：按它，確認目標是 staging，勾選 Draft 後建立。
3. 示範：標題寫「新增深色模式按鈕」，按 Create draft pull request。

**🧑 ready**：🧑 先打開 PR 的 Checks、Files changed、預覽站各看一遍（P4），再轉成 Ready for review

1. 方向：轉 Ready 之前（P4）：CI 要綠燈、PR 預覽站自己點過一遍、Files changed 沒有無關檔案——要真的打開這三個分頁，任務才會打勾。
2. 指令：到 PR 頁面依序點 Checks（全綠）、Files changed（只有 4 個檔案）、預覽站（按鈕有用），然後按 Ready for review。
3. 示範：在 PR 頁面點 Checks、Files changed、預覽站各一次，再按「Ready for review」。（沒看就按也可以，但這一格不會打勾，之後要回來補看。）

**merged**：部長審查並合併後，測試站預覽出現深色模式按鈕

1. 方向：轉 Ready 後，部長機器人會自己審查。等一下就好。
2. 指令：看右上角的通知，部長會留言。
3. 示範：如果部長退回，看他寫的原因。

**cleanup**：收尾：回到 staging、pull 最新、刪掉用完的 feat 分支（先試 -d，PR 已 Merged 再用 -D）

1. 方向：PR 合併後，那條分支就不再用了（G9）。先回 staging 並 pull。
2. 指令：git switch staging → git pull → git branch -d feat/dark-mode（會失敗！）→ 確認 PR 是 Merged → git branch -D feat/dark-mode
3. 示範：git switch staging
git pull
git branch -d feat/dark-mode
git branch -D feat/dark-mode

### 編輯器按鈕（代表你把程式寫好了）

- 「套用修改：寫好深色模式按鈕」：代表你（或 AI）已經把程式寫好了：會修改 index.html、app.js、style.css 和測試。

### 陷阱（走錯路的後果）

陷阱 id：`notes-committed`、`push-protected`、`self-merge`


### 過關畫面

- 你完成了一個功能從頭到尾的標準流程：從最新的 staging 開分支（G2）、只 add 改過的檔案（G4）、push -u、先開 Draft PR（P1）、確認後轉 Ready（P4），由部長合併（R3），最後清掉舊分支（G9）。
- git branch -d 會失敗不是你做錯：功能 PR 用 Squash and merge，GitHub 在 staging 上產生一個全新的 commit，Git 認不出你的分支內容已經合併過。只要 PR 在 GitHub 上顯示 Merged，就可以放心用 -D（G7 的例外）。
- 🧑 有幾件事只有人能做：決定該 add 哪些檔案、開 PR、自己把預覽點過一遍再轉 Ready。AI 可以幫忙跑指令，但這些判斷要你來。

這一關練到的規則：

- **G2**　分支從最新的 staging 開，命名 feat/…
- **G4**　只 add 這次真的改過的檔案，禁止 git add .
- **P1/P4**　早開 Draft PR；轉 Ready 前 CI 全綠、預覽自己點過
- **P6/R3**　功能 PR 用 Squash and merge，合併由人在 GitHub 上按
- **G7**　丟棄操作前先建備份分支；例外：PR 已 Merged 的本機分支可直接 -D（squash 讓 -d 一定失敗）
- **G9**　合併後那條分支不再使用；要接著做，從最新的 staging 開新分支

## 第 2 關　衝突

- 第 1 部　・　角色：部員　・　約 8 分鐘
- 規則：G3、P5
- 地圖卡簡介：你和小美改了同一行，她先合併了，你的 PR 出現 conflicts。

### 故事（任務卡）

你的 PR（feat/chapter-title）把第 1 章的標題改成「循環系統（含圖解）」。但小美同時間也改了同一行——改成「心血管系統」，而且她的 PR 先被合併進 staging 了。

GitHub 上你的 PR 顯示「This branch has conflicts that must be resolved」，部長也留言退回。你的電腦還停在 staging，沒有 fetch 過，看不到小美的修改。

流程：先確認自己在哪條分支（git branch --show-current）→ 切到你的分支 → git fetch → git merge origin/staging（同步 staging 一律用 merge，不用 rebase，G3）→ 🧑 在編輯器面板讀衝突記號、決定怎麼合 → add → commit → push。

### 目標與三層提示

**🧑 where**：🧑 先確認自己在哪條分支（git branch --show-current），再切到 feat/chapter-title

1. 方向：打指令之前先確認自己站在哪裡——很多「莫名其妙的衝突」是因為在錯的分支上操作。
2. 指令：git branch --show-current 看目前分支；要去你的分支：git switch feat/chapter-title
3. 示範：git branch --show-current
git switch feat/chapter-title

**merge**：用 git fetch 加 git merge origin/staging，把 staging 合進你的分支（會出現衝突）

1. 方向：要先把 GitHub 上的新狀態抓下來（fetch），再把 origin/staging 合進來（merge）。
2. 指令：git fetch → git merge origin/staging
3. 示範：git fetch
git merge origin/staging
（出現 CONFLICT 是正常的，下一步處理）

**🧑 resolve**：🧑 在編輯器面板讀衝突記號，決定標題要怎麼合，存檔

1. 方向：切到右邊的「編輯器」分頁，打開 app.js。<<<<<<< HEAD 到 ======= 是你的版本，======= 到 >>>>>>> 是小美的版本。
2. 指令：你可以按「保留我的」「保留對方的」「兩者都留」，或手動編輯。兩邊的意思都想留的話，可以手動寫成「第 1 章　心血管系統（含圖解）」。
3. 示範：沒有唯一正解——重點是你「讀過、想過」。建議手動編輯成：第 1 章　心血管系統（含圖解），存檔後記得 git add。

**commit**：git add 衝突的檔案，再 git commit 完成合併

1. 方向：解完衝突後，Git 還不知道你處理好了。先 add 那個檔案，再 commit。
2. 指令：git add app.js → git commit -m "合併 staging，解決標題衝突"
3. 示範：git add app.js
git commit -m "合併 staging，解決第 1 章標題衝突"

**push**：git push，讓 PR 的 conflicts 消失、CI 變綠

1. 方向：你的分支現在包含了 staging 的修改，可以推了。
2. 指令：git push（這條分支已經有 upstream）
3. 示範：輸入 git push

**merged**：部長確認後合併你的 PR

1. 方向：推上去後 GitHub 會重新跑 CI。綠燈且沒有衝突，部長就會合併。
2. 指令：看通知。
3. 示範：如果部長退回了，看他留的言。

### 機器人與同學的動態（走一遍選項樹時蒐集到的）

- boss：PR #12 有衝突，部長退回了。

### 陷阱（走錯路的後果）

陷阱 id：`markers-committed`


### 過關畫面

- 衝突不是壞事，是「兩個人改了同一個地方，Git 不敢替你決定」。你做對的事：先確認所在分支、fetch 再 merge origin/staging（G3：同步 staging 用 merge，不 rebase）、自己讀過兩邊的內容再決定。
- 🧑 解衝突的「決定」只有人能做——AI 可以幫你打指令，但「小美的修改要不要留」要你判斷。到下一部你會看到 AI 自作主張選一邊的後果。

這一關練到的規則：

- **G3**　同步 staging 一律用 merge，已 push 的分支不改寫歷史
- **P5**　合併前 PR 如果落後 staging，先同步並等 CI 重跑變綠

## 第 3 關　push 被拒絕了

- 第 1 部　・　角色：部員　・　約 8 分鐘
- 規則：G6、P5
- 地圖卡簡介：你的分支在 GitHub 上被別人「更新」過了。為什麼 push 被擋？怎麼辦？

### 故事（任務卡）

昨天你把 feat/chapter-count（頁尾顯示共幾章）推上 GitHub 並開了 PR。今天 PR 頁面上，部長看到分支落後 staging，按了 Update branch——GitHub 在你的分支上多做了一個 merge commit。

你的電腦完全不知道這件事。你現在想補一個小修改（頁尾文字的樣式），commit 之後 push——然後事情就不順了。

這一關練習：看懂 push 被拒絕的原因、用 pull 把 GitHub 上多出來的東西合進來、第一次 push 時用 -u 設追蹤。不要用 --force（G6）。

### 目標與三層提示

**edit**：按編輯器的「套用修改」，幫頁尾文字加上樣式

1. 方向：你在 feat/chapter-count 上。到編輯器分頁找「套用修改」。

### 陷阱（走錯路的後果）

### 過關畫面

- push 被拒絕不是壞事：Git 在保護你，免得你把別人（這次是部長按 Update branch 做的 merge commit）的工作蓋掉。正確的做法永遠是先 pull（把它合進來）、再 push；不是 --force（G6）。

## 第 4 關　在 staging 上 commit 了

- 第 1 部　・　角色：部員　・　約 8 分鐘
- 規則：G1、G7、§11
- 地圖卡簡介：不小心直接在 staging 上 commit（甚至 push）了，怎麼補救？

### 故事（任務卡）

你剛剛心急，沒有開分支就直接在 staging 上改了頁尾、commit 好了——發現的時候還沒 push。

第一個情境（4a）：先冷靜。🧑 先用 git status 看清楚現在的狀況，再把這個 commit 搬到新的 feat 分支，並讓你本機的 staging 回到跟 GitHub 一樣。

做完之後會有第二個情境（4b）：這種錯誤更慘的版本——已經 push 出去了。

### 目標與三層提示

**🧑 status**：🧑 先用 git status 看清楚狀況（別急著動手）

1. 方向：第一步永遠是看狀態——很多慘劇是因為沒看就動手。
2. 指令：在終端機輸入 git status。
3. 示範：git status（會看到「Your branch is ahead of origin/staging by 1 commit」）

**rescue**：把那個 commit 搬到新的分支（例如 feat/footer-copyright）

1. 方向：你要的 commit 已經在本機做好了，只缺一條「掛著它的分支」。
2. 指令：在 staging 上直接開新分支，commit 就會跟著走：git switch -c feat/footer-copyright
3. 示範：git switch -c feat/footer-copyright

**clean**：讓本機 staging 回到跟 origin/staging 一樣（沒有多出來的 commit）

1. 方向：現在 staging 還多著那個 commit，要讓它回到跟 GitHub 一樣。先切回 staging。
2. 指令：git switch staging → git reset --hard origin/staging（因為 commit 已經在新分支上，所以不會丟）
3. 示範：git switch staging
git reset --hard origin/staging

**revert**：4b：開一條 fix/ 分支，用 git revert 反向補一個 commit（不要改寫歷史）

1. 方向：已經 push 的 commit 不能改寫歷史（會連累別人）。改用 revert：產生一個「反向」的新 commit。
2. 指令：先 git switch -c fix/revert-footer（從 staging 開），再 git revert <壞 commit 的 sha>（用 git log --oneline 找，或在最新時用 HEAD）
3. 示範：git switch -c fix/revert-footer
git revert HEAD --no-edit

**push**：4b：把 fix 分支 push 上去（-u）

1. 方向：fix 分支也要先推上 GitHub 才能開 PR。
2. 指令：git push -u origin fix/revert-footer
3. 示範：git push -u origin fix/revert-footer

**🧑 pr**：4b：🧑 開 PR（目標 staging）、打開 Checks 看過，再轉成 Ready

1. 方向：到 GitHub 分頁開 PR，目標 staging，先用 Draft 建立（緊急修復也一樣）。
2. 指令：建立 PR 後打開 Checks 分頁確認全綠（要真的打開，任務才會打勾），再按 Ready for review。
3. 示範：部長會審查。若直接以 Ready 開出、沒看 Checks，可以回 PR 頁補看。

**fixed**：4b：部長合併後，測試站恢復正常（歷史裡那個壞 commit 仍在，只是被反向抵銷）

1. 方向：等部長合併。
2. 指令：合併後切到預覽的「測試站」看看是否恢復。
3. 示範：看右上角通知。

### 陷阱（走錯路的後果）

陷阱 id：`pushed-before-rescue`、`force-on-staging`、`direct-fix-on-staging`


### 過關畫面

- 4a：commit 還在本機時，搬家很簡單——在原地開新分支（commit 跟著走），再讓 staging 回到跟 origin 一樣（reset --hard 是 G7 的丟棄操作：這裡因為 commit 已經在新分支上，所以是安全的；不確定時先用 git branch backup/日期-說明 留一份）。關鍵是先 git status，確認自己知道現在的狀態（G1：不在 staging 上動手）。
- 4b：已經 push 的壞 commit，不能抹掉，只能「反向補一個」（git revert）。走 fix 分支加 PR，有人看過、有 CI，歷史也完整保留（§11）。reset 加 force push 是改寫別人也拉過的歷史，是更大的事故。

這一關練到的規則：

- **G1**　不在 staging／master 上直接動手，所有修改走分支加 PR
- **G7**　丟棄操作（reset、clean、branch -D…）之前，先建立備份分支 backup/日期-說明並徵得同意
- **§11**　出事時：已 push 的用 revert 補救，走 fix 分支加 PR，不要 force push

- 出事的第一原則：不要讓事情更糟。staging 是共用的，已經合併的 commit 別人可能已經拉走了；reset 加 force push 會改寫歷史，是比白屏更大的事故（§11）。
- 正確做法：用 GitHub 的 Revert 產生反向 PR。有 CI、有人看、歷史完整，#12 日後還能找回來修好再上。AI 提議破壞性操作時，規則與 Auto 模式擋住了 force，但「reset --hard」只問你——你的「不」就是最後一道防線（A2、A3）。

這一關練到的規則：

- **§11**　出事時：已合併的用 Revert 反向補救，不改寫歷史、不 force push
- **A2**　AI 要做丟棄操作（reset 等，G7）時必須先停下來問你；權限視窗就是它問你的地方，你的「不」是最後一道防線
- **A3**　AI 不得 force push、不得 push 到 staging／master（規則擋得住字面上的寫法，擋不住所有寫法）

## 第 10 關　上線

- 第 3 部　・　角色：部長　・　約 4 分鐘
- 規則：P6、R4
- 地圖卡簡介：把 staging 發布到正式站（master）。合併方式選錯，兩條分支會越分越開。

### 故事（任務卡）

本週在 staging 上累積了三個功能：章節標題改名、深色模式、收藏按鈕。測試站（staging）你已經點過，沒問題。正式站（master）還停在上週。

🧑 上線只有總負責人能做（R4，這一關你就是總負責人）：開一個 staging → master 的 PR，檢查 Checks，然後合併。

重點是合併方式。功能 PR 用 Squash and merge（P6），但「上線」這種 PR 不一樣——你可以兩種都試試看（有「時光倒流」），看看會發生什麼。

### 目標與三層提示

**🧑 preview**：🧑 先到預覽看過「測試站」和「正式站」，確認要發布的內容

1. 方向：預覽分頁可以切換環境：本機／PR 預覽／測試站／正式站。
2. 指令：把測試站和正式站各看一次，比較差在哪裡。
3. 示範：預覽 → 測試站；預覽 → 正式站。

**🧑 pr**：🧑 開一個 PR：head＝staging、base＝master

1. 方向：到 GitHub 分頁 → Pull requests → New pull request。
2. 指令：把 base 選 master、compare 選 staging。
3. 示範：標題寫「上線：staging → master」，建立。

**🧑 merged**：🧑 打開 PR 的 Checks 確認全綠，再用 Create a merge commit 合併；正式站出現新功能

1. 方向：上線 PR 的合併方式要想一下：Squash 把 staging 上很多 commit 壓成一個新 commit，Git 之後認不出它們是同一批東西。
2. 指令：選 Create a merge commit：master 上會多一個 merge commit，staging 的每個 commit 都原封不動被帶過去。
3. 示範：先在 PR 頁面打開 Checks 分頁看過（任務才會打勾），再選「Create a merge commit」，按合併。沒看就合併也可以，之後回 PR 頁補看。

### 陷阱（走錯路的後果）

陷阱 id：`squash-release`


### 過關畫面

- 功能 PR 用 Squash（歷史乾淨，一個功能一個 commit，P6）；上線 PR 用 merge commit（保留 staging 的歷史，兩條長期分支才不會越分越開）。
- 如果你試過 Squash：master 上那個全新的 commit，和 staging 上對應的那串 commit 內容相同、Git 卻認不出來。之後只要同一行再被改一次，下次上線就衝突。

這一關練到的規則：

- **P6**　功能 PR 用 Squash；staging → master 的上線 PR 用 merge commit
- **R4**　上線（staging → master）只有總負責人能做；這一關你就是
